# 评审协作章程（v1.0）

> 适用：实验三「软件实现与构建」的开发期。本文件是**执行者与评审人之间的合同**，不是交付物，不进压缩包。
> 事实源：本文件 + `协作/状态板.md` + `协作/决策日志.md` + `评审记录/` + `指示/`。聊天消息只作“触发信号”，不作证据。

---

## 1. 两个身份

| 身份 | 职责 | 不做什么 |
|---|---|---|
| **执行者（E）** | 按任务书施工、产交付说明与证据、按意见整改、维护 Git 与状态板 | 不自评通过；不改 `评审记录/`、`指示/`；不隐瞒失败；不超范围施工 |
| **评审人（R）** | 定阶段与判据（P0）、逐阶段验收、写整改意见、决定能否进入下一阶段、出终验结论 | 不写实现代码；不改 `code/`；不代替执行者做设计决策；不因个人风格偏好否决硬判据 |

**独立性要求**：R 必须①独立上下文（不看 E 的推理过程，只看交付物与证据）；②自行读取文件、自行运行检查命令，不接受 E 的口述结论；③由 R 本人写评审文件，E 只读不写。

---

## 2. 目录与写入权

```
exp3/协作/
├── 章程.md                 # 本文件；双方可提修订，改动记决策日志
├── 状态板.md               # E 维护（R 只读校对）
├── 决策日志.md             # 只追加；双方均可写，写清时间/人/事/理由
├── 模板/
│   ├── 交付说明_模板.md      # E 用
│   └── 评审意见_模板.md      # R 用
├── 交付/S<阶段>/            # E 写：交付说明.md、整改回应.md、证据清单.md
├── 评审记录/                # R 写：P0_方案评审_第N轮.md、S<阶段>_第N轮.md、终验.md
└── 指示/                    # R 写：P0_任务书.md、S<阶段>_任务书.md
```

- 交付物本体在 `exp3/code/`、`exp3/UML/`、`exp3/交付/`，不复制进 `协作/`，只引用路径与行号。
- 每个门禁通过后，E 提交一次 Git 并打标签 `gate-P0`、`gate-S0` … `gate-S9`，评审文件随该提交入库 → 评审历史与代码同源可查。

## 3. 门禁流程

```
P0 方案评审 ──► S0 立项 ──► S1 数据底座 ──► S2 领域层 ──► S3 核心业务 ──► S4 履约调度
                                                    ──► S5 报表对账 ──► S6 界面 ──► S7 质量门禁
                                                    ──► S8 Git 托管 ──► S9 报告打包 ──► 终验
```

每个阶段固定 6 拍，缺一拍不算完成：

| 拍 | 谁 | 产物 |
|---|---|---|
| ① 任务书 | R（P0 由 R 出，S1 起可沿用 P0 批准的判据并追加约束） | `指示/S<n>_任务书.md`：范围、判据、禁止事项、交付清单 |
| ② 施工 | E | 代码/文档 + 提交 |
| ③ 交付说明 | E | `交付/S<n>/交付说明.md`（模板见 §5），含证据与自检 |
| ④ 评审 | R | `评审记录/S<n>_第N轮.md`（模板见 §6），逐条给证据 |
| ⑤ 判定 | R | `通过` / `有条件通过` / `不通过`，写入状态板 |
| ⑥ 整改与复核 | E→R | `交付/S<n>/整改回应.md` 逐条回应；R 复核后改判或维持 |

### 3.1 评审门禁合并（v1.1 候选，待 CR-01 批准）

阶段仍是 10 个（判据按 `指示/P0_任务书.md`），但**送审门禁合并为 5 个**，以减少人工转达次数（评审人改为豆包后，每次评审需人工粘贴往返）：

| 门禁 | 覆盖阶段 | 一次送审内容 |
|---|---|---|
| **G1** | S0 + S1 | 骨架、venv、pylint、12 表 DDL、种子数据、行数与 `PRAGMA foreign_key_check` 证据 |
| **G2** | S2 + S3 | 领域层、状态机、仓储实现、三条关键链路、并发不超卖证明 |
| **G3** | S4 + S5 | 超时取消、入住退房、坏账、通知、报表与对账 |
| **G4** | S6 | 10 屏界面截图与交互说明 |
| **G5** | S7 + S8 + S9 | pylint 得分、覆盖率、坏味道整改、Git 历史与远程、交付包结构 |

未列入本表前，P0 任务书的 10 个阶段判据仍然逐条生效；合并只改“送审批次”，不改“判据内容”。


**轮次上限**：同一阶段最多 2 轮整改；第 3 轮不通过 → 升级为“范围重定”，R 重写任务书，E 重排计划（记决策日志）。

## 4. 判定口径

| 判定 | 含义 | 后续动作 |
|---|---|---|
| **通过** | 判据全部满足，无必修项 | 打 `gate-S<n>`，进下一阶段 |
| **有条件通过** | 无阻断项，但有必修项清单 | E 修完必修项 → R 复核（只核必修项）→ 通过；不重跑全阶段 |
| **不通过** | 存在阻断项（判据未达标/证据不足/越界） | E 返工，重新交付说明，重走 ④ |

意见级别：**必修**（阻断，必须改）、**应修**（本轮内改）、**建议**（可延后，须记入待办并说明理由）。

---

## 5. 交付说明必填字段（E）

1. **本阶段目标对照**：任务书逐条 → 做到/部分做到/未做到 + 路径
2. **变更清单**：新增/修改文件、类与函数、行数
3. **证据**：可复现命令 + 输出摘要（测试、风格、行数、并发、运行截图路径）
4. **自检结果**：通过/失败项，失败原因
5. **偏差与未完成**：与任务书/实验二设计的差异，及处理方式
6. **风险与待决**：需要 R 拍板的问题（不超过 3 条）

**禁止**：只写“已完成”“运行正常”这类无证据表述。

---

## 6. 评审意见必填字段（R）

1. **评审对象**：交付说明路径 + commit 短哈希 + 评审时间
2. **判定**：三态之一
3. **结论摘要**：≤5 行
4. **判据核对表**：判据 → 结果 → 证据（命令输出/文件:行号）
5. **逐条意见**：编号 `S<n>-R<轮>-<序号>`，级别、位置、问题、要求、证据
6. **下一阶段授权**：允许进入哪个阶段，附 3 条以内约束；或返工范围

**禁止**：无证据的意见；以“我觉得”“建议更好”为必修理由；评审期间改动 `code/`。

---

## 7. 证据标准（全阶段通用）

| 判据类型 | 最低证据 |
|---|---|
| 功能存在 | 文件:行号 + 可执行命令/用例名 |
| 功能正确 | 测试输出（用例数、断言、全绿）；关键规则给反例用例 |
| 代码规模 | 统计脚本输出的“总行/有效行”，`app/` 与 `tests/` 分列 |
| 代码风格 | pylint 配置文件 + 得分 + 整改前后对照 |
| 并发/超卖 | 并发脚本输出（N 线程、成功数、库存终值） |
| 界面 | 截图路径 + 操作步骤复现说明 |
| Git | `git log --graph --oneline` 输出 + 远程 URL |

## 8. 与本课程手册的边界（红线）

1. **实验报告由大模型起草 + 本人复核**（2026-11-25 课程侧更新要求；原手册条款“报告书写禁止用大模型”已失效，见 `决策日志.md` D-008）。边界：①每段结论必须有仓库内可核对的证据（行号、命令输出、截图）；②不得出现无法复现的数字；③本人须通读并签署“已复核”；④报告内保留 AI 参与声明与使用记录摘要。E 起草，本人复核，R 在终验时抽查“数字能否在仓库中复现”，复现不了即判不通过。

2. **不得用测试行数充软件规模**：`app/` 与 `tests/` 分列统计。
3. **不得用 `# pylint: disable` 掩盖整改**：每处禁用须写明理由并计数。
4. **不得伪造运行/测试证据**：证据必须可复现；R 有权现场重跑，重跑不一致即判不通过。
5. **代码须可对回实验二 UML**：类名、分层、仓储接口逐字对齐；偏差须列差异表。

## 9. 通信方式

- **唯一事实源是文件**。聊天消息只用于触发（“S0 已交付，请评审” / “评审完成，去读意见”）。
- R 与 E 之间不传“口述结论”；需要澄清的问题写进评审意见的“待澄清”段，E 在整改回应里答。
- 争议（判定分歧）→ 记 `决策日志.md`，由项目所有者（本人）裁决，裁决结果覆盖双方。

### 9.1 评审人 = 豆包（人工转达通道，v1.1 起）

豆包**无法读盘、无法执行命令**，所以每次送审由一个自足的文本包承担：`协作/转达包/<门禁>_发给豆包.md`。

| 环节 | 谁做 | 规则 |
|---|---|---|
| 生成转达包 | E | 按 `转达包/模板_转达包.md`；必须含“本轮判据 + 逐条证据 + 材料摘录 + 提问清单 + 输出格式”；单包 ≤ 6000 字，超了拆两包并标注“第 1/2 包” |
| 粘贴 | 所有者 | 整包发给豆包；豆包若要求补充材料，回一句“补第 N 包”，E 生成增量包 |
| 回填 | 所有者 | 豆包回复**整段**粘回给 E，E 原样存入 `评审记录/<门禁>_第N轮.md`，抬头标注 `来源：豆包（人工转达，未读文件）`，E 不得删改结论措辞 |
| 复核 | E | 若豆包的意见与可复现证据矛盾（例如它要求改一个实测已通过的判据），E 不自行改判，写进“异议”段交所有者裁决 |

**豆包评审的效力边界**：可判定“方案/思路/文档完整性/判据是否可验证/证据是否自相矛盾”；**不能**判定“代码是否真的可运行”“并发是否真的不超卖”——此类结论必须由 E 提供命令输出，豆包判的是“证据是否足以支撑结论”，不是“事实本身”。因此每包证据段必须贴真实命令与输出，禁止只写“测试通过”。

### 9.2 内部预检（非门禁，可选）

E 可在送审前用本地子代理做一次“预检”（查错别字、查判据与证据不匹配、查遗漏），预检结论**不计入门禁**，也不写入 `评审记录/`，仅用于减少豆包的往返次数。


---

## 10. 终止条件

终验（`评审记录/终验.md`）需同时满足：

1. P0 + S0–S9 全部“通过”，无未闭合必修项；
2. 交付物结构、命名、PDF、zip 与本课程手册 §A.4 一致；
3. 验收清单（`实验三_执行方案.md` §H）逐条打勾且有证据；
4. R 明确写出“项目完成 / 不完成”的结论与理由。

R 出终验结论后，E 不再自行改动交付物；如需改动，重新开一轮评审。
