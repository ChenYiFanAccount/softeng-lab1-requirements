## 3. 设计与实现要点

1. **时钟只在应用层出现一次**：`FulfillmentService` 只读 `self._clock.now()`，三条规则全部以"传入时刻"为参数。`FrozenClock.set()/advance()` 让"31 分钟后""次日 00:05"成为一次赋值，扫描是同步调用——`Ran 5 tests in 0.207s` 就是这条设计的直接结果。
2. **三条规则的顺序有意义**：先超时取消（PENDING 到期），再自动入住（CONFIRMED 且入住日已过），最后 no-show（CONFIRMED 且入住日=今天且已过 23:59）。顺序反了会出现"同一天既自动入住又判未入住"的矛盾。
3. **幂等靠状态而非标记位**：三条查询都带 `status = ...` 条件，第一次扫描把状态改掉之后，第二次扫描自然选不到它们。没有"已扫描"标志表，也没有"回补计数器"。
4. **失败审计与成功审计同一入口**：`_transition_or_record` 把被拒的异常转成一条 `DENIED:`/`REJECTED:` 记录，然后仍然提交事务、在事务外抛出异常——这样"状态没变"和"审计有记录"是同一个事务的结果，不会半途分叉。
5. **系统动作有可落库的身份**：`Actor.system()` 用 `SYSTEM_ACCOUNT_ID=0`，种子与测试夹具都插了这一行账号。这是 `stay_record.operator_id` 外键的硬约束倒逼的设计，不是可选装饰。

## 5. 偏差登记（D1–D6）

## 8. 风险与下一步

1. **截止压力**：剩余约 4.2 天，G3 = S4 + S5，S5（报表/对账 + 配置覆盖用例）约 0.4 天，之后还有 S6 界面（1.2 天）、S7 质量门禁、S8 Git、S9 报告打包。S6 是最大不确定项。
2. **扫描未做"长时间运行"验证**：`scan_once.py` 是单次触发，真实部署需要外部定时器（计划任务/cron）。报告里会说明"调度周期由外部驱动"，不假装内置守护进程。
3. **批量上限**：`batch_limit=200` 是每轮每条规则的上限，积压超过 200 单需要多轮扫描才能清空。这个取舍写在配置注释里，未做"扫描至空"的循环——避免单次扫描时间不可控。
4. **下一步 S5**：报表与对账（营收汇总、入住率、双来源对账）+ 配置覆盖用例（改 `settings.json` 后行为随之变化）。

## 9. 环境与手法备忘

- 证据生成统一用 `cmd /c "... > file 2>&1"` + `[IO.File]::AppendAllText(..., UTF8Encoding($false))` 追加 `exit=`，避免 PowerShell 把 native stderr 变成错误记录、避免 `Out-File -Encoding utf8` 写 UTF-16。
- S4-1 的"总耗时 <5s"用两种口径同时给：unittest 自报 `0.207s` 与进程级 `elapsed_total_ms=427`。
- 含反引号/`$` 的 Markdown 用单引号 here-string，双引号 here-string 会把 `` `ast` `` 变成转义序列。
