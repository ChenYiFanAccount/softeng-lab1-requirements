# 设计基线 03 · 数据设计

> 用途：报告第 4 章底稿；类图属性来源；直接回应手册 FAQ「基本功能完备性，**包括数据的存储形式**」。
> 本文件只写数据形态与约束（字段、唯一性、同步规则、索引意图），**不写建表语句**。

---

## 1. 设计原则

1. **关系型存储**：库存与价格是「房型 × 日期」的二维事实，订单是强一致单据，用关系模型 + 事务最省事。
2. **按日粒度**：库存与价格不存"区间"，逐日一行，避免区间运算与并发的边界歧义（跨日库存由逐日行保证）。
3. **订单冗余快照**：金额与单价存进订单，历史订单不随价格表变化。
4. **日志只追加**：审计表只 insert，不 update/delete。
5. **派生值不落库**：剩余可订间数、入住率等由查询即时算出（可按日预聚合缓存），不做冗余字段，避免不一致。

### 2.6 `booking` 订单
| 字段 | 约束 |
|---|---|
| 订单号 | **唯一**，业务主键 |
| 顾客 ID | 外键 → user_account |
| 酒店 ID / 房型 ID | 外键 |
| 间数 | 正整数 |

## 3. 实体关系（文字 ER，供类图/报告使用）

- `Hotel` 1 — 1..* `RoomType`（聚合：酒店存在才可挂房型）
- `RoomType` 1 — 1..* `RoomInventory`（组合：随房型生灭，按日一行）
- `RoomType` 1 — 1..* `RoomPrice`（组合：同上）
- `Booking` * — 1 `RoomType`（关联，多重度 * : 1）
- `Booking` 1 — 0..* `StayRecord`（组合：办理记录从属于订单）
- `Booking` 1 — 1 `IdempotencyKey`（一一对应）
- `UserAccount` 1 — 0..* `Booking`（关联，按角色区分顾客/操作人）
- `Hotel` 1 — 0..* `Booking`（用于本店数据隔离）
- `Booking` 1 — 0..* `NotificationRecord`
- `AuditLog` 与所有实体为弱引用（只记对象 ID，不做外键约束，避免日志被主表删除影响）

## 4. 同步更新规则（5 条，逐条挂 REQ）

| # | 规则 | 实现要点 | REQ |
|---|---|---|---|
| 1 | 下单按日扣减：对入住日至退房日前一天，每天扣减所选间数 | 同一事务，逐日加锁；任一日不足则整单回滚 | 005、019 |
| 2 | 取消 / 拒单 / 超时 / 停业 一律回补 | 与状态变更同事务；以订单状态前置判断保证只回补一次 | 007、010、012、019 |
| 3 | 改期：先占新、后放旧，整单原子 | 新旧日期两组行按固定顺序加锁，避免死锁 | 009 |
| 4 | 改价只影响新订单 | 订单存单价快照，历史单不重算 | 006、024 |
| 5 | 停售/停业只影响新订单 | 已确认订单保留，走协商取消并留痕 | 012、023 |

## 5. 库存占用口径（全系统统一，界面与查询共用）

对房型 R、区间 [D1, D2)：
`占用(R, d) = Σ 状态 ∈ {待确认, 已确认, 已入住} 的订单间数`
`余量(R, d) = 可售间数(R, d) − 占用(R, d)`
`区间可订上限 = min(余量(R, d)) for d ∈ [D1, D2)`

**三条推论（必须在报告与界面说明中出现）**：①区间内任一天余量为 0 则该房型整体不可订；②界面展示的"剩余可订间数"就是这个最小值，不是首日余量；③下单校验与查询展示使用同一口径，不允许两套算法。

## 6. 容量与保留

| 数据 | 增长方式 | 治理 |
|---|---|---|
| 每日库存 / 每日价格 | 房型数 × 90 天滚动 | 滚动生成未来 90 天，过期行归档 |
| 订单 | 按业务量线性 | 不删除，仅状态终结 |
| 审计日志 | 操作量线性，最大 | 保留 180 天，超期归档到冷存储 |
| 通知记录 | 少量 | 长期保留（用于协商追溯） |

---

## 7. 对账机制（REQ-019 / REQ-021）

每日定时任务：按房型与日期重算"可售 − 有效订单占用"，与库存表的已占用间数比对；差异 > 0 即告警并输出差异清单（房型/日期/差异值）；对账任务本身幂等，重复执行不产生重复修正。备份周期与 RTO ≤ 30 分钟在报告第 5 节说明，不在本文件展开。
