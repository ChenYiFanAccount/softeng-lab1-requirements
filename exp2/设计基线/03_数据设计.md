## 1. 设计原则

1. **关系型存储**：库存与价格是「房型 × 日期」的二维事实，订单是强一致单据，用关系模型 + 事务最省事。
2. **按日粒度**：库存与价格不存"区间"，逐日一行，避免区间运算与并发的边界歧义（跨日库存由逐日行保证）。
3. **订单冗余快照**：金额与单价存进订单，历史订单不随价格表变化。
4. **日志只追加**：审计表只 insert，不 update/delete。
5. **派生值不落库（有边界）**：区间剩余可订间数、入住率等由查询即时算出（可按日预聚合缓存），不做冗余字段。但**"已占用间数"不是派生值**——它是与"可售间数"并列的独立事实（卖出去几间），必须落库；只有"余量 = 可售 − 占用"和"区间上限 = min(余量)"才是派生。

| 地址、电话、简介 | 非空（简介可空） |
| 入驻审核状态 | 枚举（待审核/通过/驳回） |
| 驳回理由 | 可空 |

### 2.3 `room_type` 房型
| 字段 | 约束 |
|---|---|
| 房型 ID | 主键 |
| 酒店 ID | 外键 → hotel，非空 |
| 名称 | 与酒店 ID 组合**唯一** |
| 床型 | 字符串 |
| 面积 | 正数 |
| 可住人数 | 正整数（1..n） |
| **总房量** | 正整数；该房型物理房间总数，**只作"每日可售间数 ≤ 总房量"的上界**，不参与任何反推（REQ-003） |

### 2.4 `room_inventory` 每日库存
| 字段 | 约束 |
|---|---|
| （房型 ID, 日期） | **联合唯一**（REQ-003） |
| **可售间数** | 非负整数，**落库**；语义 = **当日挂牌可售总量**（酒店按日维护，已扣除维修/封房等不可售部分），恒有 `可售间数 ≤ 房型总房量`；**下单不改变它**（口径见第 5 节） |
| **已占用间数** | 非负整数，**落库**；语义 = 当日被有效订单（待确认/已确认/已入住）占用的间数，恒有 `已占用间数 ≤ 可售间数` |
| 销售状态 | 枚举（在售/停售）；停售是**开关**，不等于可售间数为 0（REQ-012） |
| 更新时间 | 时间 |

> 为什么两个数都要存：REQ-003 允许酒店把某天的可售间数**下调**（维修、封房），此时挂牌量变小而实际订单占用不变。若只存一个"剩余可订"数、再用"总房量 减去它"反推占用，就会把"不可售"误算成"已占用"（总房量 10、零订单、因维修把可售调到 7 → 反推占用 3，实际 0）。余量与区间上限才是派生值。

| 字段 | 约束 |
|---|---|
| （房型 ID, 日期） | **联合唯一**（REQ-024） |
| 单价 | 正数（分为单位存整数，避免浮点） |
| 更新时间 | 时间 |

### 2.6 `booking` 订单
| 字段 | 约束 |
|---|---|
| 订单号 | **唯一**，业务主键 |
| 顾客 ID | 外键 → user_account |
| 酒店 ID / 房型 ID | 外键 |
| 间数 | 正整数 |
| 入住日 / 退房日 | 日期，退房日 > 入住日 |
| 总价 | 整数（分）；= Σ（逐晚快照单价 × 间数），故必须有 2.7 的逐晚快照表 |
| 状态 | 枚举（6 值） |
| 幂等键引用 | 外键 → `idempotency_key`；**键值只在幂等键表存一份**，此处不重复冗余 |
| 取消原因 / 取消发起方 | 可空（顾客/酒店/系统/管理员） |
| 创建时间 / 最后变更时间 | 时间 |

**部分唯一约束（关键）**：`(顾客 ID, 酒店 ID, 房型 ID, 入住日, 退房日)` 在**状态 ∈ {待确认, 已确认, 已入住}** 范围内唯一 —— 实现 REQ-014"同一顾客同酒店同时段同房型最多一条有效订单"，已取消/已退房/未入住的旧单不阻塞新单。

> **这条索引的边界必须写进报告**：它只能拦住"起止日期完全一样"的重复；若两单日期**重叠但不相同**（如 5/1–5/3 与 5/2–5/4），索引拦不住，必须靠应用层在事务内按「房型×日期」加锁后做区间重叠校验。索引是兜底，不是唯一防线。

### 2.7 `booking_night` 订单逐晚快照（REQ-006 的核心）
| 字段 | 约束 |
|---|---|
| （订单号, 日期） | **联合唯一**；日期取 [入住日, 退房日) 内每晚一行 |
| 单价快照 | 正整数（分/晚/间），下单瞬间从 `room_price` 抄一份 |
| 间数 | 正整数（本次预订间数） |

> 为什么必须单独一张表：价格按「房型 × 日期」维护，**同一订单跨多晚时各晚单价可能不同**，单个"单价快照"字段无法表达；总价 = Σ（单价快照 × 间数）。改期重算、取消核对、报表"当时价"都依赖这张表。

| 字段 | 约束 |
|---|---|

## 3. 实体关系（文字 ER，供类图/报告使用）

- `Hotel` 1 — 1..* `RoomType`（聚合：酒店存在才可挂房型）
- `RoomType` 1 — 1..* `RoomInventory`（组合：随房型生灭，按日一行）
- `RoomType` 1 — 1..* `RoomPrice`（组合：同上）
- `Booking` * — 1 `RoomType`（关联，多重度 * : 1）
- `Booking` 1 — 1..* `BookingNight`（组合：逐晚快照随订单生灭，[入住日, 退房日) 每晚一行）
- `Booking` 1 — 0..* `StayRecord`（组合：办理记录从属于订单）
- `Booking` 1 — 1 `IdempotencyKey`（一一对应）
- `UserAccount` 1 — 0..* `Booking`（关联，按角色区分顾客/操作人）
- `Hotel` 1 — 0..* `Booking`（用于本店数据隔离）
- `Booking` 1 — 0..* `NotificationRecord`
- `AuditLog` 与所有实体为弱引用（只记对象 ID，不做外键约束，避免日志被主表删除影响）

## 5. 余量口径（全系统唯一一套：下单、回补、查询、对账共用）

**两个落库的独立事实**（REQ-003）：

- `可售间数(R, d)`：酒店按日**挂牌**的可售总量，由酒店维护（维修、封房就调小），约束 `0 ≤ 可售间数 ≤ 总房量(R)`；
- `已占用间数(R, d)`：当日被有效订单（待确认/已确认/已入住）占用的间数，由下单/回补推动，约束 `0 ≤ 已占用间数 ≤ 可售间数`。

**派生量（不落库）**：

`余量(R, d) = 可售间数(R, d) − 已占用间数(R, d)`
`区间可订上限 = min(余量(R, d)) for d ∈ [D1, D2)`

**四条必须同口径的落点**：①**下单** = 同一事务内 `已占用间数 += 间数`（`可售间数` 不动），任一日 `已占用 + 间数 > 可售` 则整单回滚；②**取消/拒单/超时/停业回补** = `已占用间数 -= 间数`（`可售间数` 不动），以状态前置判断保证只回补一次；③**界面展示**的"剩余可订间数" = 区间内各日余量的**最小值**，同时并列显示可售与已占用；④**对账**比对 `已占用间数` 与 `Σ(待确认/已确认/已入住 的订单间数)` 两条独立来源（见 §7）。

**按日调整可售（维修/封房/临时加卖，REQ-003 的合法路径，必须单独写出）**：直接把 `可售间数` 设成新值 x，**不动 `已占用间数`**；合法条件 `已占用间数 ≤ x ≤ 总房量`。这是"单一剩余量"口径无法表达的路径——下调时余量变小，但占用仍是原值。

**改总房量（N → N′）**：判据 `N′ ≥ 当日已占用间数`（任一日期不满足即拒绝，并回显当前占用数）；允许时在同事务内把该房型各日期行的 `可售间数` **钳制为 `min(可售间数, N′)`**（占用不变），任一日出现 `可售 < 占用` 则整体回滚。注意"改总房量"与"按日调整可售"是两条不同操作，报告与界面说明里不得混为一谈。

**三条推论（必须在报告与界面说明中出现）**：①区间内任一天余量为 0（或停售）则该房型整体不可订；②界面展示的"剩余可订间数"是这个最小值，不是首日余量；③下单校验与查询展示使用同一口径，不允许两套算法。

**异常清单对应**：「减房低于已售」= 上面两条路径中任一被拒的情形（改总房量时 `N′ < 已占用`，或按日调可售时 `x < 已占用`），统一返回 409 语义 + 回显当前占用数，界面 11 展示可售/占用/余量三值。

维修把某天可售从 10 调到 7 时，占用应该是 0；若用“总房量 − 可售”反推会得 3，那是把封房算成满房；所以可售与占用必须各存一列，余量才是两者相减。

| 数据 | 增长方式 | 治理 |
|---|---|---|
| 每日库存 / 每日价格 | 房型数 × 90 天滚动 | 滚动生成未来 90 天，过期行归档 |

## 7. 对账机制（REQ-019 / REQ-021）

每日定时任务（M10）：对 [今天, 今天+90) 的每一天，两边**独立**算一遍——左边读 `room_inventory.已占用间数`，右边算 `Σ(状态∈{待确认,已确认,已入住} 的订单间数)`——两者不等即**告警并输出差异清单**（房型/日期/左侧值/右侧值/涉及订单号）。**对账不自动改库存**：差异需管理员在"库存对账"页确认后，由 M3 执行修正并写审计日志（自动改库存会把 bug 掩盖掉，也无法追责）。对账任务只读、幂等，重复执行不改变任何数据。注意：对账**不比对"可售间数"**——可售是酒店挂牌量，维修、封房都会让它合法地偏离总房量，比进来就会产生假告警。备份周期与 RTO ≤ 30 分钟在报告第 5 节说明，不在本文件展开。

## 9. 唯一约束清单（"6 条"指业务唯一，技术性另计）

口径卡与执行方案里说的"唯一约束 6 条"，指的是**业务语义上的 6 条**——少了任何一条，业务规则就会被写坏。另有 4 条**技术性唯一**，只为幂等与流水不重复，不承载业务规则，故不并入 6 条。合计 10 处唯一声明，与 §2 各表"唯一约束"列逐条对应。

### 9.1 业务唯一（6 条）

| # | 约束 | 挂在 | 为什么是业务语义 | 违反时 |
|---|---|---|---|---|
| U1 | 手机号唯一 | `user_account.手机号` | 一个手机号只能是一个账号，否则"登录"无法确定身份（REQ-001/REQ-020） | 409，提示"该手机号已注册" |
| U2 | 酒店名称唯一 | `hotel.名称` | 顾客按名称搜索/识别酒店，重名会指向两个主体（REQ-004/REQ-012） | 409，提示"酒店名称已存在" |
| U3 | 同一酒店内房型名称唯一 | `room_type(酒店 ID, 房型名)` | 酒店的"大床房"只能有一个（REQ-003） | 409，提示"该酒店已有同名房型" |
| U4 | 房型 × 日期 库存唯一 | `room_inventory(房型 ID, 日期)` | 某房型某天只能有一行库存，否则"当天还剩几间"没有唯一答案（REQ-003/REQ-019） | 409，内部错误（正常流程不该触发） |
| U5 | 房型 × 日期 价格唯一 | `room_price(房型 ID, 日期)` | 同一天同一房型只能有一个挂牌价，否则算价不确定（REQ-010） | 409，内部错误 |
| U6 | 同顾客 + 同酒店 + 同房型 + 同时段，有效状态内最多一单 | `booking` 部分唯一索引，`WHERE 状态 ∈ {待确认,已确认,已入住}` | 挡住"重复提交/重复预订"（REQ-014），必须限定在有效状态内，否则顾客取消后就永远订不了同一时段 | 409，提示"你已有该时段的订单"，并把既有订单号回显给顾客 |

> **U6 的边界（必须写进报告，别当成万能）**：它只能拦住**起止日完全相同**的重复单。`1/1–1/3` 与 `1/2–1/4` 是两个不同的键，索引不会拦；区间重叠必须在应用层按"房型 × 日期"加锁后校验（见 §4 规则 1 与 §5）。把 U6 说成"能防所有重复预订"是错的。

### 9.2 技术性唯一（4 条，只为幂等与流水不重）

| # | 约束 | 挂在 | 作用 |
|---|---|---|---|
| T1 | 订单号唯一 | `booking.订单号`（主键） | 订单标识不可重复 |
| T2 | 幂等键唯一 | `idempotency_key.键值`（主键） | 同一幂等键只允许建一单（REQ-014 的第二次点击不产生第二单） |
| T3 | 订单 × 晚 唯一 | `booking_night(订单号, 日期)` | 一单的某一晚只有一条单价快照，否则总价重复累加 |
| T4 | 节假日日期唯一 | `holiday_calendar.日期` | 同日不重复登记（REQ-027），否则价格规则命中两次；停用行保留，唯一性照样拦重复登记 |

### 9.3 不写成唯一约束的三处（避免误用）

- **"同一酒店同一房型的有效订单数 ≤ 总房量"**：是**聚合约束**（跨行计数），数据库唯一索引表达不了，由 M3 在事务里逐日校验 `已占用 + 间数 ≤ 可售间数` 保证。
- **"已占用 ≤ 可售 ≤ 总房量"**：是**行内区间约束**（CHECK），不是唯一约束；`可售 ≤ 总房量` 另需触发器或应用层保证，因为要读 `room_type`。
- **"一人只能有一条（某时段）**：已由 U6 覆盖，不需要再建独立表或额外唯一索引。
