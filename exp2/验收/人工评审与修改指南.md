## 0. 先弄清三件事

| 概念 | 意思 | 你的动作 |

## 1. git 三件套（第一次做照着抄）

在 `D:\NJU\softengineering` 下打开 PowerShell，依次执行：

```powershell
# ① 看现在有什么改动（红色=未暂存，绿色=已暂存）
git status

# ② 看你到底改了什么（这一步是给你自己复核的，别跳过）
git diff

# ③ 暂存 + 提交（把 <文件路径> 换成实际文件；提交信息写在 -m 里）
git add "exp2/UML/UML类图.puml"
git commit -m "[人工] S2 类图：把库存占用改成两个独立字段，与 REQ-003 对齐"

# ④ 推到 GitHub（凭证已修好，直接推）
git push origin main --follow-tags
```

**提交信息写法**（固定三截，评审一眼能看懂）：

```
[人工] <阶段号> <一句话说改了什么>：<一句话说为什么>
```

例：
- `[人工] S2 类图：补 RoomInventory 的已占用间数属性，因为原图只有可售间数，看不出占用`
- `[人工] S5 界面03：把空态文案从"暂无数据"改成"这几天该房型已订满，试试改日期"`

**每阶段至少 1 条 `[人工]` 提交**，不要攒到最后一次性提交（历史里看不出过程）。

## 3. 每个阶段具体怎么改（照着做即可）

### S1 · 复核库存口径（10 分钟）

1. 打开 `exp2/设计基线/03_数据设计.md`，读 §5「余量口径」整节（约 30 行）。
2. 打开 `exp1/requirements.md`，找到 **REQ-003** 那一行，逐字读。
3. 问自己三个问题：
   - 酒店把某天可售从 10 调到 7（维修封房），系统里"占用"应该是多少？→ 答案应是 0。
   - 如果我原来的设计（占用 = 总房量 − 可售）会算出多少？→ 3，错。
   - 所以"两个数都要存"这句话成立吗？→ 成立。
4. **动笔**：在 §5 末尾加一段你自己的话（3–4 句），例如：

   > 我原来的想法是"只存可售、占用反推"，看起来字段更少。但 REQ-003 允许酒店按日下调可售间数，下调并不代表有人住。反推会把维修封房的日期算成"满房"，界面上占用数会骗人、对账会误报。所以可售与占用必须各存一列，余量才是两者相减的结果。代价是多一列、多一条同步责任（下单只改占用）。

5. 提交：`git add "exp2/设计基线/03_数据设计.md"` → `git commit -m "[人工] S1 库存口径：补一段我对『两个数都要存』的理解，因为反推会把维修封房算成满房"`

### S2 · 类图 / 包图（15 分钟）

1. 打开 `exp2/UML/UML类图.puml`，找 `class RoomInventory`，确认三行属性在：`可售间数`、`已占用间数`、`销售状态`。
2. 挑一处**你认为不对或不够清楚**的地方动手，任选一个：
   - 把某个多重度改得更准（例如 `Booking "1" --> "1..*" BookingNight` 你如果觉得一晚也可能没有快照，就改成 `0..*` 并想清楚为什么）；
   - 给 `Booking` 加一个你认为报告会用到的属性（如 `创建时间`）；
   - 在 `BookingStateMachine` 旁加一行注释：`' 状态只能经此修改，直接改状态字段一律拒绝`。
3. 重新出图：`D:\softeng-env\bin\puml.cmd exp2\UML\UML类图.puml`（会覆盖同名 png），打开 png 看你改的地方生效了没。
4. 提交 puml 与 png **一起**：`git add "exp2/UML/UML类图.puml" "exp2/UML/UML类图.png"`。

### S3 · 状态图（10 分钟）

1. 打开 `exp2/UML/UML状态图.puml`，找到 5 条禁止转换的注释块。
2. **补后果**：每条禁止转换后面加半句"为什么不能"，例如：
   - `已入住 → 已取消 : 不允许（客人已实际入住，取消会让已发生的住宿变成无账可对）`
3. 提交，并在报告 3.3 里引用你这句（这正好是评审说的"补后果"，也是你的人工落点）。

### S4 · 时序图（8 分钟）

1. 打开 `exp2/UML/UML时序图-下单锁库存.puml`，数一下 `已占用间数 += n` 这条消息在不在事务括号内。
2. 挑一条消息把措辞改准确，例如把 `扣减库存` 改成 `占用间数（已占用 += 间数，可售不变）`。
3. 提交。**红线自查**：如果"占用"被画在事务外，必须挪进去——这是 S4 的唯一红线。

### S5 · 界面 03（10 分钟）

1. 用图片查看器打开 `exp2/UI界面/界面03.png`。
2. 看空态与错误态文案，判断一个真实顾客能不能看懂。**改文案的方式**：找到生成这个界面的 HTML（`exp2/UI界面/_src/界面03.html`），改文字 → 用 Edge 无头重新截图（命令见 `实验二_执行方案.md` B 节链路②）→ 覆盖 `界面03.png`。
3. 参考改法：`暂无数据` → `这几天该房型已订满，换两个日期或看看同类酒店`；`库存不足` → `刚被别人订走了，余量已更新，返回重选`。
4. 提交。报告 6.1 里把"为什么这样写"写一句（文案是给谁看的、解决哪个误解）。

### S6 · 界面 11（10 分钟）

1. 打开 `exp2/UI界面/界面11.png`，确认四个数都在：可售间数、已占用间数、余量、总房量。
2. 你判断哪一列该更醒目：如果顾客/酒店工作人员更容易误读"余量"，就把它加粗或换色，并在说明里写一句理由。
3. 提交。

### S7 · 报告 3.4 设计理由（20 分钟，**这条最重要**）

1. 打开 `exp2/实验报告.md` 的 3.4 节（五条设计理由）。
2. 挑其中一条（建议"库存口径"或"依赖倒置"），**合上文档，用你自己的话重写那一段**（150–250 字）。写完再对照原文，看你有没有漏掉"代价"那半句——设计理由的价值在"我付出了什么"，不在"我有什么优点"。
3. 句式模板（填自己的判断）：

   > 我一开始想的是 ______，因为它 ______。但 ______ 这个场景会出问题：______。所以改成 ______。代价是 ______，我认为可以接受，因为 ______。

4. 提交。这一段同时充当报告正文与 AI 章节里"修改优化后的结果"的证据。

### S8 · AI 使用章节（40 分钟，**整章以你为主**）

手册要求：**每一次使用 AI 都要记录**，四要素齐——使用场景 / 生成结果 / 优缺点分析 / 修改优化后的结果；章末答两问。

1. 打开 `exp2/实验报告.md` 第 8 章，里面已有我搭好的表格骨架（AI-01…）。
2. 对每一条，**先看我写的"生成结果"摘要，再补你自己那两栏**：
   - 「优点」写它省了你什么（时间/结构/覆盖度）；
   - 「问题」写你实际发现哪里错（这里必须真，写错的地方就是我返工过的地方，如库存口径、界面 15 三合一、7 条 vs 8 条）；
   - 「你的处理」写你怎么改的，并指向具体提交号（`git log --oneline --grep=人工` 可以查）。
3. 章末两问，**用自己的判断答**（各 200–300 字）：
   - 问一：大模型如何辅助软件设计？→ 建议按"它能做什么/它做不好什么/人还剩什么"三段答；
   - 问二：能否设计一套工作流让人只做检查校对？→ 建议答"能，但边界在哪"：机械一致性可脚本化（我们就有 `验收/check.py`），语义判断与取舍不能；给出你的流水线（生成 → 机械校验 → 人工判断 → 回写基线）并说明哪一步必须人。
4. 提交。**这一章是终检重点**：评委会对照 git 历史看你写的改动是否真的发生过。

## 6. 常见错误（第一次做最容易踩）

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 攒到最后一次性提交 8 条 | 历史看不出"逐阶段人工介入"，D-04 仍判不达标 | 每阶段收尾当天提交 |
| 只改错别字/空格 | 不算实质性修改 | 改语义：补信息、删多余、改判断 |
| 改了 puml 没重新出 png | png 与 puml 不一致，终检直接挂 | `puml.cmd` 重新渲染后再 add |
| 报告里写"AI 生成了完美方案" | 与 git 历史矛盾，评委一问就露 | 写真实缺陷 + 你怎么发现的 |
| 用 `git commit --amend` 改历史 | 已推送的提交会被强推破坏评审基线 | 新开一条 `[人工]` 提交 |
