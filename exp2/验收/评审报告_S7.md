## 1. 站得住的部分（先说好的，免得改坏）

- **1.2 把四个口径前置定死**（六状态八边 / 库存三值 / 下单只加占用 / 一单多晚价），后面各章不再重复解释——这是整篇报告最省读者力气的一处安排，也是"设计有主线"的证据。
- **3.1 架构选型**没有停在"我们选了模块化单体"，而是给出两个被否方案**各自的致命问题**（微服务会把"读余量—判断—写占用"的三步窗口变成跨进程窗口），并写明代价（单模块无法独立扩容）+ 为什么这个代价可接受（200 并发、P95 ≤1.5s）。这一段是老师最想看的。
- **3.6 决策-理由-代价表**（7 行）把"我为什么这么做、付了什么钱"一次说清；`幂等键与订单同事务写 / 先占位后回滚会留孤儿键`、`对账只告警不改库存` 两条尤其到位。
- **3.5 八张图每张都有"为什么这样设计"**，且写的是**踩过的坑**而不是图注复述：类图那段讲"早期只存一个可售数、占用靠反推，被 REQ-003 的维修封房打脸"；时序图二那段讲"第一版没有数据库生命线，两个扫描实例同时跑就双回补"。这是本实验最容易拿分也最容易空转的地方，现在没有空转。
- **4.3 库存三值 + 5.1 四道闸门**：行锁 → 锁内复核 → U6 唯一索引 → 对账只告警，四道写清"缺一不可"，且明确"对账不自动改数，避免把错误掩盖成正常"。
- **6.4 三种"没东西"用"重试有没有意义"一句判据**切开空态/错误态/不可用态，并把原稿的错误（把空态写成策略说明）写进去——这类"改前改后"的痕迹正是 AI 章节要的素材。
- **附录 A** 27 条全文 + 每条"异常与边界"引用块完整，与 `exp1/requirements.md` 一致（抽查 001/018–027 逐字对过）。

## 2. 必修 A（中）｜第 6 章没有"每个界面的功能描述"

手册要求报告含"**各模块的 UI 界面及其功能描述**"。现在第 6 章只有：一张 17 行映射表（界面 / 页面 / 模块 / REQ）、4 段"关键界面取舍"（11/13/16/17）、一张三态表。**17 张界面里有 13 张在正文只有一行表格**，没有入口路径、页面元素、主流程、异常文案——这跟"界面说明"是两回事，等于把交付物退化成一张目录。

改法很省力：`UI界面/界面说明.md` 里那 17 行已经是"目标用户 → 入口路径 → 页面元素 → 主流程 → 异常文案"的完整五元组，直接改写成 6.3 的正文（每界面 3–5 句），6.2 的表保留作索引。预计 1–1.5 小时。若还想更稳，挑 6–8 张代表图嵌进 PDF（03/04/05/07/11/13/17），**但必须用压缩版**（见 §4-D），否则 PDF 体积再涨 5MB。

## 3. 必修 B（中）｜3.4 对交互矩阵的三处转述与矩阵本身不符

`02 §3` 的矩阵我逐格数了一遍：**S 单元格共 7 个**——`M2→M3 初始化库存行`、`M5→M1 权限`、`M5→M3 扣减`、`M6→M3 回补`、`M6→M5 改状态`、`M7→M3 回补`、`M7→M5 改状态`。报告 3.4 却写"矩阵里 **9** 个 S 是关键"，具体列的名字也对不上：

| 报告 3.4 的说法 | 矩阵实际 |
|---|---|
| "矩阵里 9 个 S" | **7 个 S** |
| "`M5→M9`（写审计）" 列为 S | M→M9 全部是 **A（异步）**，这正是"主链路不依赖通知/审计成功"的设计意图 |
| "M6 不能直接改库存（必须经 M5 编排）" | 矩阵里 `M6→M3` 是 **S（回补）**，M6 确实直接调 M3 |

三条里第一条是数错、第二条是把 A 说成 S（还把"异步审计"这个刻意的设计说反了）、第三条是转述与矩阵打架。改法：把"9 个 S"改成"7 个 S"，审计那句改成"审计一律 A（异步），失败不影响主流程、靠重放补"，M6 那句改成"M6 负责编排与判定，扣减/释放的具体动作仍由 M3 的接口在**同一事务内**执行"——这样既准确，又把"谁决策、谁执行"的分工说清了。10 分钟的事，但被问到就是硬伤。

## 4. 必修 C（中-高，工程）｜A 层对第 7/8 章零校验，空壳照样 33/33

第 7 章现在只有一句"本章由 S8 撰写……本节先留结构"，第 8 章同样；`--stage 7` 仍然 **33/33 全绿**。这不是 S7 的错（按计划第 7/8 章归 S8），但它说明一件事：**33 项判据里没有一项在验证"AI 章有没有正文"**。33 项全是结构性判据（章节顺序、图注出现次数、REQ 出现次数、禁用词、字数）——这些恰好都满足"空壳也能过"。这就是上次 `acceptance-script-negative-test` 里那类"永远通过"的判据：**PASS 只证明结构没缺，不证明内容成立。**

S8 交付时必须同时补三件事，否则 S9 终检没有刹车：

1. 第 7 章 **≥ 6 条记录**（S1 库存口径 R-01、S2 实体类型 R2-01~03、S3 加锁与读取 R-08、S4 超时扫描 R-10/R-11、S5 三态区分、S6 两条路径拆分），每条含 6 要素：使用场景 / 输入 / 原样结果 / 发现的问题 / 人工改后 / 工具优缺点。
2. 第 7 章带一张**人工修改对照表**：6 条 `[人工]` commit 的 hash + 一句话改了什么（`2686e23` / `1d48c09` / `391d4aa` / `13b693e` / `7684412` / `fff3023`）——手册要的"人工修改记录"靠这张表落地，不靠自述。
3. 第 8 章两个问题各 ≥ 300 字（AI 如何辅助设计 / 能否做成"人只做检查校对"的工作流，且工作流要给出**可执行的检查清单**，比如"每张图反向核对 REQ / 状态转换与 01 §2 对表 / 库存三值在四处一致"）。

同时给 `check.py` 补 5 条判据：第 7 章记录条数 ≥ 6、每条 6 要素齐全、含 6 个 commit hash、第 8 章两问字数、报告不出现"见 S8"字样。**判据要能让现在的空壳 FAIL**——这是唯一能证明它不宽松的办法（可以先注入一次空壳跑负向测试，再还原）。
