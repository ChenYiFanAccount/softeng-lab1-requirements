## 0. 设计口径（三张表、两个按钮、一套徽标）

| 事项 | 口径 | 依据 |
|---|---|---|
| 库存三值 | **可售（酒店挂牌）/ 已占用（有效订单）/ 余量 = 可售 − 已占用**；下单只加已占用，改可售不动占用 | `设计基线/03_数据设计.md` §5 |
| 六状态徽标 | 待确认（琥珀）、已确认（蓝）、已入住（绿）、已退房（灰）、已取消（紫）、未入住（红） | `设计基线/01_术语与追溯.md` §2 |
| 可执行动作 | 按钮是否可点由状态决定；不可点必须**置灰并说明原因**，不靠点击后报错 | 01 §2 禁止转换、REQ-010 |
| 错误提示 | 一律就地提示（输入框下方红字）或页面顶部红条，**不清空已填内容、不弹窗打断** | REQ-020、评审 D 系列 |
| 角色越权 | 返回 403 并提示「无权访问该资源」，不是静默失败 | REQ-020 |
| 金额与时间 | 价格按「房型 × 日期」逐晚展示；时间一律 `YYYY-MM-DD`、倒计时用「分:秒」 | REQ-004、REQ-005 |

## 3. 这批界面刻意没做的事（免得评审判成"功能漏了"）

1. **没做真实图片**：酒店图用渐变占位块，因为实验二只要求界面设计，不要求素材；报告里写清"图片位为占位，交付实现时替换"。
2. **没做支付**：REQ-022 一期不做在线支付，界面 05/09 里只有"应付金额/预计退款"两个只读值。
3. **没做多语言与移动端**：只交付 1440×900 桌面端一套。
4. **界面 01 的图形验证码是静态图**：示意验证码过期与就地报错的交互，不做真实校验。

## 4. 空态 / 错误态 / 不可用态：三种"没东西"不是一回事

| 情形 | 用户看到什么 | 给不给重试 | 落点 |
|---|---|---|---|
| 空态：条件成立，但确实没有数据 | 说清"哪段时间没房" + 替代路径（换日期 / 换酒店） | 不给重试，重试也还是没房 | 界面 03 底部提示、界面 07 订单空态 |
| 错误态：请求失败（超时、服务不可用） | 红条「加载失败，点击重试」 | 必须给，且已填条件不能丢 | 界面 03、05 顶部红条 |
| 不可用态：有数据，但当前用户不能操作 | 置灰 + 写明原因（无权限 / 停售 / 不在可取消区间） | 不给重试，重试也没用 | 界面 07 动作列、界面 08 「标记未入住」 |

> 这一节是我加的判断：原稿把三者都叫"异常文案"，混在一起写，结果界面 03 把空态写成了
> 一段策略说明——用户看不出"现在到底发生的是哪一种"。分开的标准就一条：**重试有没有意义**。
> 有意义的才是错误态，才配重试按钮；另外两种给的是替代路径和原因，不是重试。
