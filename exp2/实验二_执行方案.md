矩阵解读（报告必须写，这是"交互"而非框图的核心）：M5→M3 的 **S** 是下单占用（`已占用间数 += n`，可售间数不动）与重复校验的同一事务；M6→M3 的 **S** 是超时取消释放（`已占用间数 -= n`）；M7→M3 的 **S** 是取消释放；M10→M6 的 **T** 只是调度器按阈值**触发** M6 的扫描任务（M10 不碰订单与库存），置取消与释放由 M6→M5、M5→M3 的 S 在同一事务内完成。**R 全部是只读**：M5→M4 的 R 只借"区间余量取最小值"口径算可订上限，不写不占；M10→M3 的 R 是对账读取，**只告警不改库存**。

**五条设计理由（一条一段，直接进报告 3.4 节）**

1. `超卖次数 = 0`（REQ-019）→ 占用与重复校验同事务、库存按「房型×日期」行级加锁、并配唯一索引兜底 + 对账任务。
2. `改期整单原子`（REQ-009）→ 先占新日期、成功后再释放旧日期，失败整单回滚。
3. 价格快照（REQ-006）→ 单价按「房型×日期」维护，故下单时把**每一晚**的单价与间数写入 `booking_night`（订单逐晚快照），订单总价 = Σ(单价×间数)；之后改价只影响新单，旧单金额可逐晚追溯。
4. `30 分钟可配置`（REQ-005）→ 超时阈值进配置中心，定时任务按阈值扫描待确认订单。
5. 日志只追加 180 天（REQ-017）→ 独立审计模块，业务模块只能写不能改，查询权限仅管理员。

## F. 数据设计（**12 张表**；手册 FAQ 明确要求"包括数据的存储形式"，必须单列一节）

| 表 | 关键字段 | 唯一约束 |
|---|---|---|
| `user_account` | 账号、角色、手机号、口令哈希 | 手机号唯一 |
| `hotel` | 名称、地址、电话、简介、审核状态 | 酒店名称唯一 |

| `room_inventory` | 房型、日期、**可售间数**（酒店按日挂牌）、**已占用间数**（有效订单占用）、销售状态 | （房型, 日期）唯一；**两个数都落库**：`可售 ≤ 总房量`、`占用 ≤ 可售`；余量 = 可售 − 占用 是派生 |
| `room_price` | 房型、日期、单价 | （房型, 日期）唯一 |

| `booking_night` | 订单号、日期、单价快照、间数 | （订单号, 日期）唯一；[入住日, 退房日) 每晚一行，总价 = Σ(单价×间数) |
| `idempotency_key` | 键、关联订单号、创建时间 | 键唯一 |
| `stay_record` | 订单号、动作（入住/退房/no-show）、操作人、标记来源（人工/系统）、时间 | — |
| `audit_log` | 操作人、角色、对象、动作、变更前状态、变更后状态、时间 | 只追加，保留 180 天 |
| `notification_record` | 订单号、通知时间、协商结果 | — |
| `holiday_calendar` | 日期 | 日期唯一 |

**同步更新规则（5 条）**：下单按日**占用间数**（`已占用 += n`，可售不动）；取消/超时/拒单按日**释放间数**（`已占用 -= n`）；改期先占新后放旧、整单原子；改价只影响新订单；停售/停业只影响新订单、已确认订单保留。**可售间数只由酒店按日调整（维修/封房），下单与释放都不动它**；`已占用间数` 必须落库，`余量 = 可售 − 占用` 才是派生（口径见 `设计基线/03` §5）。
**索引意图**：查询按（城市, 日期）走组合索引；余量查询按（房型, 日期）区间扫；订单列表按（顾客, 创建时间倒序）、（酒店, 状态, 创建时间倒序）。
**容量与保留**：每日库存/价格按「房型×90 天」滚动生成；审计日志 180 天滚动归档。

| AI-02 | 类图 | 是否漏幂等键 / 逐晚快照 / 办理记录；关系是否全画成普通关联、缺多重度 |
| AI-03 | 状态图 | 是否把禁止转换画成允许；双触发边是否被合并；守卫条件是否缺失 |
| AI-04 | 界面布局 | 搜索结果是否缺余量口径；预订页是否缺倒计时与价格明细；有无空态/错误态 |
| AI-05 | 数据约束 | 是否只用普通唯一索引；是否漏"有效状态内部分唯一"与"改期先占后放" |
| AI-06 | 报告文字 | 是否通篇"高效、稳定、友好"；设计理由是否只给结论不给"为什么"与代价 |

每条固定五行：**使用场景 / 生成结果（概述，不复述全部内容）/ 优缺点分析 / 修改优化后的结果 / 我的判断（采纳了什么、否决了什么及原因）**。
章末两问的写法（各 300–500 字，必须有自己的体验）：
- ① 大模型在设计各环节能到什么程度：起稿、扩面、查漏有效；定架构取舍、判断"这样设计是否合理"、界面可用性判断无效。
- ② "人只做检查校对"的工作流：需求作唯一事实源 → 模板与约束前置 → 机器可校验清单（REQ 覆盖率、术语一致性、状态可达性、多重度完整性、图可渲染、模块↔界面一一对应）→ 人只做通过/驳回 → 改动后 diff 回归。**诚实结论：目前能到"人做决策 + 校对"，到不了"只校对"**，因为"为什么这样设计"与"界面好不好用"没有可自动化的判据。
